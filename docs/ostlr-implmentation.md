# Ostlr —— 多窗口 AI Agent 统一管理器 · 设计基线 v0.6

> 状态：方向已定，进入 M0 验证。
> **本文件是交给 `steve` skill 的设计输入**：它需要同时具备"痛点到体验"的定义与"技术上已经查实的事实"，才能产出可执行方案。所以本文件**不删技术决策**，也不删痛点。

## 0. 一页速览

**它是什么**：一个本地桌面面板，把正在跑的多个 agent（Claude Code / Codex / proJV / 任意 shell）列在一起——三秒内知道"谁在跑、谁在等我、谁该被杀"，并且能就地在这个目录起一个新的 TUI、把路径送进你想送的那个 TUI。

**它不是什么**：不是终端模拟器，不是 proJV 的子项目，不做云端/远程，不写各家的配置。

**四件事，一件比一件贵**：

| 层 | 能力 | 用户感知 | 里程碑 |
|---|---|---|---|
| L1 | **看**：会话列表 + 状态 + 资源 | "我知道现在有几个 agent，谁卡在审批上" | M1 |
| L2 | **管**：聚焦 / 终止 / 重启 | "不用开任务管理器" | M1 |
| L3 | **起**：从目录一键起指定 TUI | "两次点击就有新会话，不用记命令" | M1 |
| L4 | **送**：把路径或 `@路径` 送进指定 pane（注入方式按该 CLI 的习惯），并明确告诉用户送给了谁 | "复制粘贴不再贴错窗口" | M2 |

## 1. 要解决的问题

这是本项目的立项依据，也是验收的第一层。**列"今天的做法"，是因为痛点必须落在具体动作上，否则没法验收。**

| # | 痛点 | 现状（今天的做法） | Ostlr 的解 | 验收（怎么算解决了） |
|---|---|---|---|---|
| P1 | 多窗口项目失忆 | 开多个 agent 窗口，记不清哪个是哪个项目 / 模型 / 分支；切回来要 cd 一遍确认 | 会话列表绑定"工作区路径 + 分支 + agent + 窗口"；点一下聚焦 | 同时跑 3 个 agent，扫一眼能说出"哪个窗口是哪个项目/分支" |
| P2 | 注意力分散 | 不知道哪个在跑、哪个在等我、哪个已经卡住；靠切窗口肉眼确认 | 状态汇总 `working / blocked / idle / done / error / unknown` + 托盘徽标 | 有 agent 在等审批时，30 秒内面板变色 + 托盘提示 |
| P3 | 文件操作断层 | 路径靠手打或从资源管理器复制，文档树看不见 | 文件树 + 一键复制绝对路径（单个按钮） | 一次点击完成"路径进剪贴板"，无需打开资源管理器 |
| P4 | 图像引用困难 | TUI 里没法把图片喂给 agent，只能手打路径 | 文件树按钮 → 向当前 pane 注入路径或 `@路径`（按该 CLI 的习惯） | 在 Ostlr pane 内一次点击完成注入（外部会话退化为剪贴板 + 提示） |
| P5 | 资源不可见 | 多个 agent 跑起来看不到谁吃 CPU/内存 | 侧栏进程级资源（整棵进程树聚合） | 能一眼看出哪个 agent 吃满 CPU / 内存 |
| P6 | 进程管理靠系统 | 只能切系统窗口，杀进程要开任务管理器 | 面板内：聚焦 / 终止（递归子进程）/ 重启（原 cwd） | 三件事都在面板内一点完成，不离开 Ostlr |
| P7 | 窗口管理靠系统 | 平铺 WM 做不好分屏与持久化 | 仅 Ostlr 自己的 pane 做分屏 / 标签 / 布局持久化；外部窗口只做"聚焦 + 平铺排列" | 重启 Ostlr 后，自己的布局恢复原样 |
| P8 | 多厂家割裂 | 每家配置 / 会话各一套，找不到"上次那个会话" | 只读汇总各家的会话目录与最近会话 | 一个面板看到所有 CLI 的会话位置与最近会话 |

**优先级**：P1 / P2 / P6 是"每天都在痛"的，M1 必须全解；P3 / P4 / P5 次之；P7 / P8 最后。

**为什么不把 P2 做成"自动推断"**：屏幕正则推断会把"等待"误报成"空闲"，这是这类工具最贵的错误（U5）。所以状态走协议与 hook，推断只做兜底且必须标 `unknown`。

## 2. 目标与非目标

**目标（按验收顺序）**

- G1 让"我有几个 agent、谁在等我"变成**三秒内的视觉判断**，而不是切窗口确认。
- G2 让"在这个目录起一个指定 TUI"变成**两次交互**，且失败时能自己说清原因。
- G3 让"把路径送给哪个 agent"变成**不可出错的动作**（目标可见、跨项目有警告）。
- G4 在需要看画面时**不必离开 Ostlr**（M2 才做；M1 用系统终端即可）。

**非目标**

- 不做通用终端模拟器，不与 Windows Terminal / Ghostty / WezTerm 竞争。
- 不自研 VT 解析 / 字形图集 / 输入法。
- 不代替人做权限审批（Ostlr 只把人送到现场）。
- 不做云端 / 远程 / SSH 中转（v1）。
- 不写各家的配置文件（只读）。
- 不用 GPL 组件（理由见 §4.6）。

**成功判据**：M1 交付后连续使用两周——若"打开真终端"的需求 < 每天 1 次，则 M2 不做，产品定版。

## 3. 体验设计

### 3.1 界面结构

```
┌ Ostlr ──────────────────────────────────────────────────────────────────────┐
│ [＋ 新建会话] [刷新] [全部聚焦]        等待中: 2   运行: 3   内存: 1.2 GB     │  ← 顶栏
├───────────────────────┬─────────────────────────────────────────────────────┤
│ 会话（左，可折叠）      │  主区（右）                                          │
│ ─────────────────────  │  ┌── 标签: claude·proJV │ codex·sop-test ──┐        │
│ ● claude  proJV        │  │                                         │        │
│   D:\ws\proJV  main    │  │        终端区（M2 才有；M1 这里是空状态） │        │
│   等审批 40s  212MB    │  │                                         │        │
│ ─────────────────────  │  └─────────────────────────────────────────┘        │
│ ○ codex   sop-test     │                                                     │
│   D:\ws\sop-test        │  ┌── 文件树（右下） ──┐  ┌ 详情（可折叠）┐         │
│   运行中     98MB      │  │ D:\ws\sop-test     │  │ 命令、cwd、  │         │
│ ─────────────────────  │  │  ├ src/            │  │ 启动时间、   │         │
│ ◌ projv_tui relic      │  │  ├ docs/           │  │ 状态历史     │         │
│   未知         —       │  │  └ CMakeLists.txt  │  │              │         │
├───────────────────────┴──┴────────────────────┴──┴─────────────────────────┤
│ 就绪 · 已复制 D:\ws\sop-test\src\main.cpp → Pane「claude·proJV」            │  ← 状态栏
└─────────────────────────────────────────────────────────────────────────────┘
```

| 区域 | 作用 | 出现时机 |
|---|---|---|
| 顶栏 | 新建、刷新、全局动作、汇总计数 | 常驻 |
| 会话列表 | 每行：状态点 + agent + 项目 + 分支 + 状态词 + 耗时 + 内存 | 常驻（M1 核心） |
| 主区 | M1 空状态/欢迎页；M2 终端 pane（标签 + 分屏） | M1 / M2 |
| 文件树 | 浏览 + 右键（启动 / 复制 / 注入） | 常驻（L3 入口） |
| 详情 | 选中会话的命令、cwd、启动时间、状态历史 | 可选 |
| 状态栏 | **所有"送路径"的结果与目标都在这里**（U3 的落点） | 常驻 |
| 托盘 | 数字徽标 + 悬停摘要 + 点击唤起 | 常驻 |

### 3.2 状态图例（全应用唯一语义）

| 符号 | 状态 | 颜色 | 含义 | 是否打扰 |
|---|---|---|---|---|
| ● | `blocked` | 醒目 | **需要人**（权限 / 提问 / 认证） | 置顶 + 托盘计数 +（可选）提示音 |
| ◐ | `working` | 正常 | 正在干活 | 不打扰 |
| ○ | `idle` | 灰 | 闲着 | 不打扰 |
| ✓ | `done` | 绿（3 秒） | 刚完成 | 不打扰 |
| ✕ | `error` | 红 | 出错，附最后一行 | 托盘计数 |
| ◌ | `unknown` | 灰 + 问号 | 数据不足，**不猜** | 不打扰 |

### 3.3 流程：在某个目录起一个 TUI（L3）

**三个入口，同一个选择器**：

| 入口 | 触发 | 预填目录 |
|---|---|---|
| 文件树右键目录 | 「在这里启动…」 | 该目录 |
| 文件树右键文件 | 「在所在目录启动…」 | 文件父目录 |
| 顶栏「＋ 新建会话」/ 会话列表空白右击 | 新建 | 上次使用 / 最近目录 |

```
┌ 新建会话 ────────────────────────────────────────────┐
│ 目录  [ D:\ws\proJV                     ] [浏览…]    │
│ 启动  ● claude           claude --resume             │
│       ○ codex            codex                       │
│       ○ projv_tui        D:\ws\proJV_tui.exe         │
│       ○ PowerShell       powershell.exe              │
│       ○ 自定义…           （编辑 config.toml 模板）   │
│ 位置  (•) 新窗口（外部终端）   ( ) Ostlr 内新标签 ← M2 前置灰 │
│                                     [取消]  [启动]    │
└─────────────────────────────────────────────────────┘
```

规则（每条都有验收含义）：

1. **可用性预检**：每个模板在打开选择器时即检查 PATH / 配置路径，未找到的置灰并在同一行给修复提示（"未找到 claude：请安装，或在 config.toml 写绝对路径"）。→ 对应风险 R4。
2. **记住上次**：目录、agent、位置三项都记住，下次预填——这是"两次点击"的实现基础（U2）。
3. **启动即反馈**：会话列表立刻出现一行 `starting…`，成功后 300ms 内变为真实状态；失败时该行就地变红并附原因，**不弹窗、不吞按键**（U4）。
4. **环境注入**：`cwd` = 所选目录；模板可注入 `TUI_EXECUTION_FILE`、`PROJV_WORKSPACE` 等变量。

### 3.4 流程：把路径送进 TUI（L4）

| 动作 | 送到哪 | 说明 | 可用条件 |
|---|---|---|---|
| **复制路径** | 剪贴板（绝对路径） | **只有一个按钮**，不给选择——多数时候人只是想把它贴到别处 | 总是可用 |
| **注入纯路径** | PTY stdin | 给"把路径当普通文本/参数"的 CLI（shell、多数 TUI） | 仅 Ostlr 自己的 pane（M2） |
| **注入 `@` 引用** | PTY stdin | 给把 `@file` 当文件引用的 CLI（Claude Code / Codex 等） | 同上 |

**为什么注入要两个而不是一个**：`@` 不是通用语法——有的 CLI 把 `@path` 解析成文件内容，有的把它当普通字符串（于是 agent 看到一个字面量 `@`）。这属于"每家交互不一样"，Ostlr 不猜：

- 每个 agent 模板里声明默认注入方式（`inject = "path" | "at"`），UI 把默认那个做成主按钮，另一个放在它的下拉/右键里；
- 注入默认**追加一个空格、不回车**（留给用户自己确认或继续补字），是否追加可在模板里配（`inject_suffix`）。

**目标判定（显式，不许猜）**：有聚焦 pane → 它；无聚焦但有"最近活跃 pane" → 它，且提示注明"（最近活跃）"；都没有 → 只进剪贴板并提示"无目标 pane，请手动粘贴"。

**三段式回执（本流程的核心，也是"标注"的实现）**：

```
已复制          D:\ws\sop-test\src\main.cpp  →  Pane「claude·proJV」   ✓ 同一项目
已注入(路径)    D:\ws\sop-test\src\main.cpp  →  Pane「claude·proJV」   ✓ 同一项目
已注入(@)       D:\ws\sop-test\src\main.cpp  →  Pane「codex·sop-test」 ! 目标在 D:\ws\proJV
```

配套视觉反馈：目标 pane 标题闪 800ms；跨项目用警告色并给一句原因；注入成功后**不弹任何东西**（文本出现在那个 pane 里就是证据），状态栏回执 5 秒后淡出。

**为什么不做"自动粘贴到外部窗口"**：外部窗口没有可控输入通道，模拟按键会打错地方。v1 只做剪贴板 + 回执；等 M2 有了自己的 pane，注入才是一等公民。

**键盘约定**：右键菜单为主；`Ctrl+Shift+C` 在焦点不在 pane 内时由 Ostlr 拦截为"复制路径"，焦点在 pane 内则让给终端（避免抢掉终端的复制）。

### 3.5 流程：需要你的时候（L1/L2）

| 事件 | 界面反应 | 明确不做 |
|---|---|---|
| 某会话进入 `blocked` | 列表置顶 + 状态点醒目 + 托盘徽标 +（可选）提示音；悬停显示原文（"claude 想删除 build/，等你批准"） | 不弹模态、不抢焦点 |
| `error` | 该行变红，附最后一行错误；托盘计数 | 不自动重启 |
| `done` | 短暂闪绿，3 秒后归为 idle | 不弹窗 |
| 全部 idle | 顶栏计数归零，托盘无徽标 | — |

**点一下就到位**：点会话行 → 外部会话聚焦其窗口（必要时最小化遮挡），内嵌 pane 切标签并聚焦输入区。**不代替人回答审批**——权限语义属于各家 CLI，v1 只负责把人送到现场。

### 3.6 流程：结束、重启与退出

- **终止**：确认框显示将结束的进程树（含子进程与内存）；确认后递归结束；该行转 `done(exit 1)`，详情保留命令与耗时。
- **重启**：同 cwd、同命令、同尺寸；`pid` 变但条目位置不变（用户不会"找不到刚才那个"）。
- **退出 Ostlr**：外部会话不受影响（我们不是它们的父进程）；内嵌 pane 会随之结束 → 退出前明确提示"N 个内嵌会话将结束，[仍然退出] [取消]"。

### 3.7 体验验收（U1–U6）

| # | 目标 | 验收方式 |
|---|---|---|
| U1 | 三秒知情 | 扫一眼面板就能说出：几个会话、几个在等、几个报错 |
| U2 | 两次交互起会话 | 选目录 → 点「启动」；agent 选择在同一个对话框内完成 |
| U3 | 送路径零歧义 | 动作后 2 秒内能从状态栏读出"送给了哪个 pane、它属于哪个项目" |
| U4 | 不打扰 | 不抢焦点、不弹模态、不吞键；只在 `blocked` / `error` 提示 |
| U5 | 永不误报 | 数据不足显示 `unknown`；绝不把"在等"显示成"空闲" |
| U6 | 可恢复 | Ostlr 重启后布局恢复；退出不残留子进程 |

## 4. 技术方案

### 4.1 主栈与许可

| 层 | 选型 | 许可 | 为什么是它 |
|---|---|---|---|
| 语言 | Python 3.11+ | PSF | 本产品 80% 代码是"拼数据源"；同能力 C++ 约 3–4 倍代码量 |
| UI | **PySide6** | LGPLv3 | 官方 Qt 绑定；`PyQt6` 是 GPLv3/商业双授权，分发麻烦 |
| PTY（Windows） | **pywinpty**（ConPTY） | MIT | Jupyter/terminado 同款，生产验证；`PtyProcess.spawn(cmd, dimensions=(rows,cols))` + `read/write/setwinsize` |
| PTY（Unix） | ptyprocess / 标准库 `pty` | MIT / PSF | 20 行适配层统一接口 |
| 终端画面 | **xterm.js** + `QWebEngineView` + `QWebChannel` | MIT | VT 渲染与 IME 由它承担（VS Code 在用的路径），我们一行 VT 代码都不写 |
| VT 解析（可选） | pyte | LGPL | 只在"不显示画面但要屏幕文本"时用 |
| 进程 / 资源 | psutil | BSD-3 | 进程树、cwd、CPU、内存、递归终止 |
| 窗口操作 | pywin32 | PSF | `EnumWindows` / `GetWindowThreadProcessId` / `SetForegroundWindow` |
| 文件监听 | watchdog（或 30 行轮询） | Apache-2.0 | 监听状态目录 |
| 托盘 | pystray | LGPL | 徽标与悬停摘要 |
| 打包 | PyInstaller（或 Nuitka） | GPL with exception / Apache-2.0 | 目录模式，预计 150MB+（含 Chromium） |

许可结论：**LGPL + MIT + BSD + Apache，无 GPL 传染**，将来要闭源分发也不受阻。

### 4.2 数据源三条（互不依赖，可分别实现与验收）

| 数据 | 来源 | 关键实现点 |
|---|---|---|
| 进程 / cwd / 命令行 / 分支 | `psutil` + `git -C <cwd> branch --show-current` | Windows 上取他人 cwd 靠 psutil 读 PEB，**要求同权限**（否则只读降级，见 R6） |
| 窗口（聚焦 / 最小化 / 标题） | `pywin32` | 抢前台会被 Windows 拦：`AllowSetForegroundWindow` + `AttachThreadInput` 兜底（R5） |
| 资源 | `psutil` 聚合整棵进程树 | 子进程要递归，agent 常带多个子进程 |
| 状态 | L1 / L2 / L3（§4.3） | 三级叠加取最高可信 |

### 4.3 状态来源阶梯（核心机制）

| 级 | 来源 | 前提 | 可信度 | 用在哪 |
|---|---|---|---|---|
| **L1** | **OSC 7501**（Program Status Protocol，2026-10-06） | 我们拥有该会话 PTY 并**回答探测** | 最高（CLI 主动上报，含原因与原文） | 内嵌 pane 主来源 |
| **L2** | hook 写状态文件 | CLI 支持 hooks | 高（结构化，但依赖厂商 hook 面） | 外部会话主来源 |
| **L3** | 窗口标题 / 最后事件距今 | 以上都无 | 低 | 只标"疑似卡住"，不用于"在等" |

**L1 的两个实现义务**（M0 必须验证，见附录 B）：

1. 收到 `ESC ] 7501 ; ? ST` 要**立刻**回同形应答，否则 CLI 整场沉默（协议是静默失败设计）。
2. **抢在 DA1 之前回答**：Claude Code 用 DA1 当哨兵，DA1 回复先到就把"支持 7501"判为否且整场不再翻转（已知缺陷 claude-code#105534）。
3. 自己的 DA1 应答要声明足够能力（真彩色、光标样式、括号粘贴），否则 CLI 降级。

**Windows ConPTY 已知限制**（必须在 M0 实测，不实测不许写进结论）：

- conhost 的 VtEngine 认 **CSI / OSC / DCS**，但**不认 APC**（Kitty 图形那类载荷会被静默丢弃）。
- `PSEUDOCONSOLE_PASSTHROUGH_MODE`（0x8，Win11 22H2+）本意直通原始流，但**部分 build 上标志被接受、未知序列仍被剥**。
- 因此 OSC 7501 属于"认识的家族"，通过概率较高，但**必须实测**；失败即整体退 L2，不硬啃。

**L2 契约**：`%LOCALAPPDATA%\ostlr\status\<pid>.json`，写入用"临时文件 + 原子改名"：

```json
{"ts":"2026-10-30T20:11:03Z","source":"claude-code","pid":12345,
 "cwd":"D:/ws/sop-test","state":"blocked","kind":"permission",
 "msg":"Approve rm -rf build?"}
```

规则：`state ∈ {idle, working, blocked, done, error}`；`blocked` 必须带 `kind ∈ {permission, question, auth}`；**过期即未知**（`now - ts > 90s` 且无 L1 → `unknown`）；pid 已退出 → 转 `done`，10 分钟后清理。

### 4.4 三种所有权边界（别混）

| 形态 | 拥有 PTY？ | 能拿到 | 代价 |
|---|---|---|---|
| **外部会话**（覆盖 P1/P5/P6） | 否 | 进程、cwd、窗口、资源；状态只能靠 L2 | 拿不到屏幕内容与 L1 |
| **Ostlr pane**（覆盖 P3/P4/P7） | 是 | 状态、尾行、注入、分屏、布局 | Ostlr 崩了 pane 跟着死（v1 接受，见 R9） |
| 只读观察（P8） | 否 | 会话目录、配置 | — |

**M1 只做"外部会话"**——它覆盖 80% 的日常痛，且完全不碰终端渲染。

### 4.6 被否决的方案（连同原因，避免重走）

| 方案 | 否决原因 |
|---|---|
| C++ + ImGui 自绘终端 | ImGui 生态没有可用的 PTY+VT 组件；**IME 是空白区**（`BACKENDS.md` 把 IME 列为 optional）；代码量 3–4 倍 |
| C++ + librio / coffer / libghostty-vt + 自写渲染 | 引擎不是瓶颈，**字形图集 + 输入法**才是；Python 借 xterm.js 直接绕过 |
| QTermWidget（lxqt） | 上游只支持 BSD/Linux/macOS，**PTY 层不支持 Windows**；PyPI 绑定只发 manylinux/macOS wheel；**GPLv2+** |
| py3qterm / pyqtermwidget | PyQt5 时代、GPLv3、无 Windows、多年未动 |
| Electron / Tauri | 等于把 Python 那 800 行换成 JS，丢掉 psutil/pywin32 的顺手，收益不明 |
| tmux / zellij | Unix 优先、Windows 不可用；也没有审批与资源诉求 |
| 依赖微软 Intelligent Terminal | 它是终端不是调度器；作为用户默认终端共存，而非依赖 |

### 4.7 代码量与工期对照

| 能力 | Python 实现 | C++ 实现 |
|---|---|---|
| L1 看 + L2 管 + L3 起（M1） | 800–1500 行 / 1–2 周 | 3000–5000 行 / 4–6 周 |
| L4 送（M2，含 pane） | +500–800 行 / 1–2 周 | +IME 一个月起 |

### 4.8 硬约束（`steve` 不得违反）

1. **v1 不写 C++**；不自研 VT 解析、字形图集、输入法。
2. **许可红线**：只用 LGPL / MIT / BSD / Apache；QTermWidget 系列（GPL）不得进入依赖树。
3. **状态不可推断成 `idle`**：不确定就 `unknown`（U5）。
4. **M1 必须两周内可用**；不得为 M2 的 pane 提前开工。
5. **外部窗口不得模拟按键**（不可靠）：只做聚焦 + 剪贴板 + 回执。
6. **退出不得留下孤儿进程**；内嵌 pane 结束前必须明示（U6）。

## 5. 里程碑（DoD 双视角：用户能做什么 + 技术上验了什么）

### M0 · 状态可达性验证（3–5 天，无界面）

- **要回答的问题**：在**我们的 PTY/ConPTY** 里，真实 CLI 的 OSC 7501 到底能不能收到；我们的应答它认不认。
- **harness**：直接使用**已实现该协议的开源 CLI**（候选与确认方法见附录 B），不自写 emitter——自写 emitter 只能验证"我们对规范的理解"，容易自证，测不出真实实现的行为。
- **交付**：一个 30 行左右的 pywinpty 脚本 + 一份实测记录（OS / conhost 版本 / CLI 版本 / 收到的报文 / 失败形态）。
- **DoD（技术）**：在 ConPTY 里跑通至少一个真实 CLI，日志中出现 `state=working` 与 `state=blocked`（含 `kind`）。
- **停手**：两个不同 CLI 都收不到 → 放弃 L1，状态全走 L2，**直接进 M1**（M1 不依赖 L1）。

### M1 · 看板 + 启动器（1–2 周）— 最小可用形态

- **交付**：会话列表（P1/P2）、聚焦/终止/重启（P6）、资源（P5）、托盘提醒、文件树 + 启动选择器（L3）、路径复制与三段式回执（L4 的剪贴板形态）。
- **内部顺序**：列表能看（1–2 天，自己当天就能用）→ 启动器（3–4 天）→ 回执与提醒（2–3 天）。
- **DoD（用户视角）**：
  1. 同时跑 3 个 agent，扫一眼知道谁在等（U1）；
  2. 在 `D:\ws\sop-test` 起一个 Claude，两次交互完成（U2）；
  3. 杀掉一个 agent，条目自动消失、不残留（U6）；
  4. 复制路径后，状态栏能读出"送给了哪个项目"（U3）。
- **DoD（技术视角）**：进程树递归正确；无孤儿进程；启动失败有可读原因；抢前台失败有降级路径（任务栏闪烁）。
- **停手**：用满两周，"想在这个窗口里直接看/敲"的需求 < 每天 1 次 → **定版在 M1**。

### M2 · 内嵌 pane（1–2 周，按需）

- **交付**：主区终端 pane（xterm.js）+ 分屏/标签/布局持久化（P7）+ 两种注入（纯路径 / `@路径`，P4 的完整形态）+ L1 状态（M0 通过才有）。
- **DoD**：pane 里能跑 `vim` / `htop` / `claude`；中文输入正常；注入后目标 pane 有回显且状态栏有回执；重启后布局恢复（U6）。
- **停手**：内存 > 1.5GB 或输入延迟可感知 → 砍到最多 2 个 pane，其余仍走外部窗口。

### M3 · 增强（1 周，按需）

多目录批量启动、外部窗口平铺、等待超时升级提醒、状态历史（谁卡最久）、只读汇总各家会话目录（P8）。

| **M0+M1** | **约 2 周** | **每天能用的管理器**（L1+L2+L3 全通） |

## 8. 与 proJV 的关系

- **Ostlr 独立**：proJV 对 Ostlr 而言只是"可被纳管的一个 agent 源"，与 claude / codex 同级。
- **proJV 侧只加一件小事**：作为程序端发送 OSC 7501（约半天）——状态变化时发、stdout 非 TTY 时不发、退出时 `clear`。独立价值：任何支持该协议的宿主（Windows Terminal / Intelligent Terminal / Ghostty / Ostlr）都能看到 proJV 在 `working` / `blocked`。
- **不做反向集成**（把面板嵌进 proJV）：调度器塞进 agent 会让两者都复杂；需要交互时用"聚焦窗口"松耦合。
- 商业化只在一种形态下成立：**卖管控**（权限策略、审计、团队状态汇总），个人版保持免费本地。不在 v1 范围。

### B.1 第一步不是跑，是**确认它真的实现了**

### B.3 宿主侧脚本（约 25 行）

```python
from winpty import PtyProcess
import re, threading

PROBE   = b"\x1b]7501;?"                       # CLI 的探测
REPLY   = b"\x1b]7501;?\x1b\\"                 # 唯一合法应答（原样回，缺省代表支持五种状态/三类原因）
REPORT  = re.compile(rb"\x1b\]7501;(.*?)\x1b\\")

p = PtyProcess.spawn("crush", dimensions=(40, 120))

def pump():
    while True:
        try: data = p.read(4096)
        except EOFError: return
        if not data: return
        if PROBE in data:
            p.write(REPLY)                     # 先回 7501，再让 DA1 的应答排在后面
            print("[host] replied to probe")
        for m in REPORT.finditer(data):
            body = m.group(1).decode("utf-8", "replace")
            if body != "?": print("[host] STATUS:", body)

threading.Thread(target=pump, daemon=True).start()
input("按回车结束\n"); p.terminate(force=True)
```

### B.4 判据与诊断阶梯

| 检查 | 通过标准 | 不通过说明什么 | 下一步 |
|---|---|---|---|
| A | 日志出现 `state=working` | ConPTY 剥了 OSC，或应答没送到 | 试 `PSEUDOCONSOLE_PASSTHROUGH_MODE`(0x8)、旁加载 conpty.dll、记录 conhost 版本 |
| B | 日志出现 `state=blocked` 且带 `kind` | 同上 | 同上 |
| C | 同一会话**持续**上报（不止启动一次） | 应答不被接受（缺能力清单） | 按规范补应答字段 |
| D | Claude Code 出现 idle→working | DA1 竞速（已知缺陷） | 7501 立即回、DA1 延后；仍失败 → 退 L2 |

A/B/C 过 = L1 可用；D 失败不影响 M1（外部会话走 L2）。
